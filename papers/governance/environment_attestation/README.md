# Environment attestation (M-030 / EXP-004)

Generated by `papers/scripts/make_environment_attestation.py`. Re-check an existing
record without re-running anything:

```
python papers/scripts/make_environment_attestation.py --verify
```

## What it establishes

A green `attestation.json` means **all three** of the following held at generation time:

1. **The stack is inside the declared envelope.** The installed interpreter and the
   versions of numpy/scipy/pandas/matplotlib were checked against the ranges declared
   in `pyproject.toml`. This is the condition that makes the rest meaningful — a green
   suite on an out-of-envelope stack attests nothing about the *supported*
   configuration, which is the claim the manuscript actually makes.
2. **Two identical all-green suite runs.** The full suite ran twice with
   `--junitxml`; both reported zero failures and zero errors, and both collected the
   same number of tests. Two runs also rule out a result that depends on ordering or
   on state left behind by a previous run.
3. **Every release gate returned an accepted exit code** — build hygiene,
   provenance-claim consistency, cross-format parity, document consistency, and both
   Word validators.

   Only `document-consistency` accepts a non-zero code. It exits **2** when a field the
   *author* must supply (e.g. suggested reviewers) is still unfilled — blocking for
   submission, but not a defect in the tree and not something tooling can resolve.
   Its exit **1**, meaning two copies of the same fact have drifted apart, is a real
   failure and breaks the attestation. Each gate's `accepted_exit_codes` and `ok` flag
   are recorded per gate, so an author-pending state stays visible rather than being
   smoothed into a pass.

The generator refuses to write `green: true` unless all three hold, so the file cannot
record a pass that was not earned.

## What it does *not* establish

- **It is not a CI attestation.** It records one run on one machine, identified in the
  `platform` and `git` blocks. It is evidence that the declared configuration works,
  not that it works everywhere in the declared range.
- **It does not pin the exact tested tree unless the working tree is clean.** The
  `git.dirty` flag records this honestly. When `dirty` is `true`, the commit in
  `git.head` does *not* fully identify what was tested — regenerate the attestation
  after committing if the record needs to be commit-exact.
- **It says nothing about the optimizer evidence.** Run correctness, seeds, and
  byte-stability are covered by the evidence release and its own manifests; this file
  covers only the software state.

## Refreshing

Regenerate after any change to the test suite, the gates, the dependency pins, or the
declared envelope in `pyproject.toml`. It is cheap (two suite runs plus the gates) and
a stale attestation is worse than none, because it reads as current.
